## What is implemented

| Component | Result |
| --- | --- |
| Additive migration | `Sources/App/Migrations/CreateCanonicalDrawings.swift` adds `drawing_assets`, `drawing_processing_jobs`, `drawing_asset_pages`, `drawings`, `drawing_versions`, `drawing_version_pages`, `snag_drawing_pins` and `drawing_pin_events`. Existing photo and legacy synced-drawing schemas are unchanged. `configure.swift` adds one registration after the existing metadata migration. |
| Scope constraints | Composite project/workspace, version/drawing/asset/project and page/asset/project foreign keys prevent crossing two assets even inside one project. Current-version scope is a deferred constraint so initial drawing/version creation can commit atomically. |
| Immutable source and history | Original identity, owner, project, purpose, expected hash/size/MIME, generated key and processor profile cannot be rewritten. Once recorded, processing identity and first publication time remain immutable. SQL triggers reject update/delete of processed pages, versions, version-page mappings and pin events. Destructive migration revert is explicitly refused. |
| Typed internal contracts | `Sources/App/DTOs/CanonicalDrawingDTO.swift` defines closed drawing-source purpose, allocation, publication, page geometry, processing lease/result and pin commands/receipts. Asset responses contain no storage key or public URL. Trusted processor results are not HTTP inputs. |
| Allocation and processing state | `CanonicalDrawingService.allocate` validates filename, declared hash/MIME/size and current internal edit permission, then stores actor-scoped idempotency receipts. Source keys are generated from scoped UUIDs. `beginProcessing` grants a bounded lease; only the current unexpired lease may commit. A reclaimed lease invalidates the previous worker. |
| Processing manifest acceptance | `finishProcessing` rechecks project/uploader authority after the processing interval, verifies manifest identity against allocation, mathematically consistent page geometry/transform, declared page/output limits, contiguous indices and output hashes. It records all immutable pages and readiness in one transaction. Exact completed retries preserve page identity; altered output conflicts. UUIDv5 derives asset-page IDs from a fixed namespace and asset/index. |
| Initial publication | `publish` requires ready owned source, expected asset revision, explicit acknowledgement of internal original-source access and valid selected sheets. It preserves each supplied native drawing UUID and stable version/page UUID. One canonical drawing represents one selected sheet. All selected drawing/version/page rows, source publication and receipt commit together. Missing pages, reused IDs or a replacement attempt roll back the entire command. |
| Pin transactions | `setPin` checks current edit permission, project/snags, expected snag/pin revisions, finite normalised coordinates and exact active same-project page. It updates current pin/tombstone, native-compatible snag drawing scalars, snag revision, immutable event and receipt together. Events retain previous/next page and coordinates, server actor and the actual snag revision at mutation time. |
| Protected lifecycle | New pin mutations cannot alter closed, Awaiting-review or archived snags; an exact previously committed receipt remains recoverable after those later state changes without rewriting state or history; archived/unmanaged projects cannot invoke writes. A legacy drawing reference without a canonical pin must be reconciled/imported first. Removing a pin retains its identity/history; replaying an earlier placement returns its historic receipt without resurrecting the current pin. |
| Read/replay authority | Current project ACL is checked before receipt replay. Unpublished source metadata is uploader-only, including against a company owner; published source metadata becomes readable to current internal project readers. Removed access or archived project blocks subsequent read/replay. Viewer permissions use the existing central policy; public Viewer provisioning remains outside this work. |

`DrawingGeometryValidation.swift` defines affine coefficients as `[a,b,c,d,tx,ty]`, mapping raw PDF user-space points (y up) into normalised display coordinates (y down). It checks the effective media/crop intersection, all four rotations, positive UserUnit, coefficients and transformed corners, with at most one pixel of rendering aspect rounding. Origin and coefficient errors are measured relative to page extent/normalised display units, and aspect tolerance is in pixel space; large world coordinates or tiny page units do not relax the checks. Raster sources instead use upright pixel coordinates (y down), equal zero-origin boxes and no PDF rotation. Actual decoder/renderer facts still require future byte-level verification.

All mutation paths use the existing workspace lock shared with membership/grant changes. Operations own their transactions and receipt locks. Global entity locks use deterministic order when publishing several sheets. No opaque report JSON is used as project authority. Typed page geometry is immutable per-page metadata, not a replacement for normalised graph relationships.

## Deployment and startup migration implications

`configure.swift` registers `CreateCanonicalDrawings` after `CreateProjectMetadataParity` in the existing startup `autoMigrate()` chain. Deploying this source to an enabled database-backed app therefore applies the eight new tables, indexes, functions and triggers on first migration; registration is not an inert documentation change. Do not replace the frozen `91a53d9` image or point a new binary at retained review/recovery/production databases as a test shortcut.

The migration is one transaction and supports repeated prepare without changing existing rows; the new current-version foreign key is deferred only within its publication transaction. Applying it requires the candidate migration role's table/index/function/trigger privileges. The isolated test role proved this in the test database; actual staging privileges, migration ledger, startup readiness and multi-container migration scheduling remain unverified. No real worker startup, object store or provider exchange is established by the database suite.

Before staging promotion, export a new immutable source/image checkpoint, verify its exact migration ledger and private-storage/runtime configuration, then follow the existing disabled-first runbook. Do not run a down migration to remove this foundation: `revert` deliberately refuses, and immutable records/history are retained. An older compatible reader must still preserve existing comment-redaction protections. Once drawing routes/graph writes are eventually enabled, any rollback must understand their purpose/scope/coverage restrictions or disable that capability explicitly; startup success alone is insufficient.

## Deliberate activation boundary and remaining work

**Do not attach a controller to these mutation methods yet.** They do not emit drawing entities into `platform_changes`, because the currently served register cannot bootstrap that graph or project its complete dependency group. Pin writes are likewise internal-only until complete journal emission, snapshot/delta projection and Contractor page selection/revocation can be committed with them. Calling them from a public route prematurely would leave existing clients with incomplete change coverage.

The fixed profile `drawing-initial-v1` is a manifest identity, not a validated production processor build.

Drawing metadata/archive/restore commands, verified source-PDF provenance/import receipts, legacy dates/ownership reconciliation, explicit Contractor page prepare/activate/read/revoke, exact report page/version manifests and four-surface geometry tests. No automatic replacement/pin migration is supported.
4. Native immutable import/outbox/acknowledgement and checksum-verified fresh-device reconstruction under the real account-scoped store/media adapter. This backend slice does not change native files or correct missing legacy source associations.
5. Original-to-annotated raster version relationships, remaining folders/tags/organisation graph and full R1/R4/D2 acceptance. Historical editable vectors or unknown provenance must not be fabricated.

A compatible rollback must retain immutable records, existing comment-redaction protections and future purpose/coverage restrictions. The down migration intentionally does not delete drawing data.
